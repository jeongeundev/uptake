# PRD: uptake

## 목표
오픈소스 저장소에 **결합된 채로 존재하는 개발 방법론**을 재사용 가능한 **파라미터화된 패턴**으로 추상화해, 다른 프로젝트에 **검증과 함께** 이식한다 — "오픈소스가 코드에 해준 것을 개발 방법론에 한다."

## 사용자
검증된 저장소들이 **실제로 어떤 개발 규율로 굴러가는지 알고**, 그것을 손으로 역설계하지 않고 자기 프로젝트에 적용하고 싶은 **개발자 / 소규모 팀**.

주 사용자는 **무엇을 찾을지 이미 아는 사람이 아니다.** "무엇을 원해야 하는지 모르는 상태"에서 출발하는 사람이다 — 하네스·루프 엔지니어링이 유행하는 것은 알지만 자기 저장소에 어떻게 적용하는지는 모르는 상태. 정리된 목록은 이미 세상에 많고, 부족한 것은 **그래서 내 저장소에 어떻게 적용하는가**다. 이 판단이 제품 루트를 SURVEY로 정한 근거다(ADR-017).

- 사용자는 **드라이버**다 — 패턴을 고르고, 생성된 diff를 검토·승인한다 (human-in-the-loop).
- 이식 결과물의 **소비자**는 타깃 repo의 개발 루프 전체 — 사람 **그리고** 그 repo에서 일하는 코딩 에이전트. 에이전트가 자동으로 방법론을 따르게 되는 것은 repo-native 산출물의 **부수효과**이지, 별도의 주 사용자가 아니다.

## 핵심 기능
사용자가 겪는 순서로 세 가지다 — **이 저장소는 어떻게 개발하는가 → 다른 곳들도 그렇게 하는가 → 내 프로젝트에 심는다.** 셋은 별개 제품이 아니라 **같은 데이터(패턴)의 세 가지 뷰**이며, 데이터 성숙도의 세 단계(`observed` → `corroborated` → 이식 가능)와 겹친다.

각 패턴은 5-구성요소 스키마로 기술된다: **의도 · 불변 구조(역할) · 결합점(파라미터) · 출처(provenance) · 판별 오라클**. 그리고 직교하는 두 축으로 분류된다 — `capability`(*생성형 `generative`*: 통과/실패를 판별할 오라클이 있다 / *서술 전용 `descriptive`*: 없다)와 `evidenceStatus`(*`observed`*: N=1 / *`corroborated`*: 독립 근거 N≥2).

1. **발견 — 이 저장소는 어떻게 개발하는가 (SURVEY · 제품 루트)**
   사용자가 **저장소만 지정**하면 앱이 그 저장소의 개발 체계 후보를 제시한다 — 각 후보는 의도 서술과 **실재하는 근거 경로**를 달고 나온다. 사용자는 무엇을 찾을지 떠올릴 필요 없이 **제시된 것 중 고른다**(ADR-017). 고른 후보는 `observed`/`descriptive`로 등재되며, 이 단계의 산출물은 "이 repo가 실제로 이렇게 한다"까지만 주장한다(ADR-006).

2. **대조 — 다른 곳들도 그렇게 하는가 (추상화 · 핵심 가치)**
   **≥2개 실재 repo를 대조**해 스택-불변 **본질**(의도 + 불변 구조)과 스택-종속 **결합점**(파라미터)을 분리한다(EXTRACT→ABSTRACT). 복사가 근본적으로 못 하는 유일한 것 — "원본 스택에서 떼어내기" — 을 한다. 단일 관찰은 `observed`에 머물고, 대조로 검증되면 **`corroborated`(N≥2)** 로 승급한다.
   *"나와 비슷한 프로젝트는 어떻게 하는가"* 는 이 축의 제품 표면이다 — **핵심 기능이되, 단일 저장소 분석 결과의 공통 스키마와 비교 가능성이 검증된 이후 단계다**(아래 'MVP 제외' 참조).

3. **이식 + 검증 — 내 프로젝트에 심는다 (증명)**
   타깃 repo의 **결합점을 자동 탐지**해 패턴을 재생성하고(INSTANTIATE — 생성물엔 **왜(근거) 주석 + provenance**를 단다), 두 방향으로 실제 검증한다(VERIFY):
   - **양성**: 준수 상태 → 게이트 green
   - **음성**: 심어놓은 스펙 위반 → 게이트가 red로 **잡아냄**
   음성 테스트가 물어야만 추상화가 성립했음이 증명된다. **diff 미리보기 → 명시적 승인** 후에만 타깃 repo에 적용한다.

**순서가 뒤로 갔다고 중요도가 내려간 것은 아니다.** 3번은 1번 결과의 유일한 품질 판정 장치다 — "LLM이 이 repo는 X를 한다고 말했다"와 "그 X를 심었더니 위반이 red로 잡혔다" 사이의 거리가 uptake와 링크 모음집을 가르는 전부다(ADR-017).

## MVP 수용 기준
이 프로젝트는 자기가 설파하는 방법론을 dogfooding하므로, PRD 자체가 **테스트 가능한 스펙**이어야 한다. 아래 기준은 구현 전에 그대로 테스트로 옮겨진다. 하나라도 red면 MVP는 완성이 아니다.

| ID | 기준 | 검증 |
|---|---|---|
| AC-1 | 각 `corroborated` 패턴은 서로 다른 `independenceGroup`을 가진 `sources` **≥2개**를 갖고, 그중 최소 하나가 `isTargetStack: false`다. 세는 대상은 **근거 파일(provenance)이 연결된 source뿐**이다. **못 만족하면 로드 거부**(선언과 근거의 불일치 = 데이터 오류, 조용한 `observed` 강등 없음) | `independenceGroup` distinct <2 fixture · 전부 `isTargetStack: true`인 fixture 각각이 로드 거부되는지 검사. 판정값 자체는 큐레이터가 부여한다(ADR-005) |
| AC-2 | **로드 거부(하드 게이트)**: provenance resolve 실패, `sources`·`provenance` 빈 배열, 참조 무결성 위반(**양방향** — 가리키는 대상 없음 / **고아 source** / **고아 role**), `capability`↔`oracle` **양방향** 불일치, `observed`인데 독립 그룹이 1이 아님 | 거부 사유별 fixture 각각에 대해 로드 거부 검사. **더미-source fixture**(근거 파일 없는 source로 `independenceGroup`만 채워 `corroborated`를 노리는 케이스), **고아 role fixture**(근거 없이 선언된 역할), `observed`인데 독립 그룹 0개·2개인 fixture 포함 |
| AC-2b | **역할 단위 대조**: `corroborated` 패턴의 **각 role**은 서로 다른 `independenceGroup`의 provenance ≥2개로 뒷받침된다. 한 repo에서만 관찰된 것은 `roles`(본질)가 아니라 `bindingPoints`(차이)에 속한다 | role별 독립 그룹 수 검사. **role A는 repo1에서만, role B는 repo2에서만 관찰된 fixture**가 로드 거부되는지 — 패턴 전체 N≥2만으로는 대조 추상화가 성립하지 않음 |
| AC-3 | **생성 차단(소프트 게이트)**: 로드된 패턴 중 `observed`이거나 `descriptive`인 것은 카탈로그에 **보이되** 생성이 비활성이다 | `observed` / `descriptive` / 둘 다인 조합 각각을 UI·엔진 양쪽에서 차단 검사 |
| AC-4 | 타깃 repo에서 패턴의 각 결합점을 **근거 파일과 함께** 제시한다. 탐지 실패한 결합점은 `binding-unresolved`로 표시하고 사용자 입력을 받는다 | fixture repo에 대해 결합점별 값+근거 경로 검사, 미탐지 케이스 포함 |
| AC-5 | 생성·검증 전 구간에서 **타깃 repo는 수정되지 않는다** | 검증 전후 타깃 repo 작업 트리 동일성 검사 (git status + 파일 해시) |
| AC-6 | 양성: 생성물을 적용한 격리 워크스페이스에서 게이트가 **green** | 준수 fixture 실행 |
| AC-7 | 음성: 오라클이 정의한 위반을 심은 워크스페이스에서 게이트가 **red**로 잡는다. red의 정의는 exit code가 아니라 **리포터 출력상 `oracle.gateTestId` 테스트의 실패**다 | 위반 fixture 실행. 삽입 불가 fixture(경로 이탈, `marker` 0회·2회 이상)는 `injection-failed`로 거부되는지 함께 검사 |
| AC-7b | **인프라 오류는 음성 성공이 아니다** — 리포터를 산출하지 못한 실행(설치 실패, 설정·문법 오류, spawn 실패, signal, timeout)은 `gate-error`이며 이식이 중단된다 | 각 오류를 심은 fixture가 `gate-error`로 보고되는지 검사. **깨진 vitest 설정 fixture가 "위반을 잡았다"로 계산되지 않는 것**이 핵심 케이스 |
| AC-8 | 음성이 green이면 이식 전체가 **실패**로 표면화되고 적용이 차단된다. 이 실패는 일반 테스트 실패와 **구별되는 상태**(`negative-not-caught`)로 보고된다 | 판별력 없는 게이트(항상 green) fixture가 실패로 보고되는지 검사 |
| AC-9 | 사용자가 승인한 diff는 **검증에 사용된 산출물과 동일**하다. 불일치 시 적용을 거부한다 | 승인 직전 산출물 내용 해시 재확인 테스트 |
| AC-10 | 타깃 repo 쓰기는 **사용자 승인 후에만** 일어난다 | 승인 없는 경로에서 쓰기 호출이 없음을 검사 |
| AC-11 | 소스 스택 ≠ 타깃 스택인 이식 한 건이 고름→탐지→생성→양성/음성→승인→적용까지 끝까지 통과한다 | E2E 시나리오 1건 |
| AC-12 | 실행되는 게이트 커맨드는 이식 실행 개시 전 사용자에게 **표시된 것과 동일**하다. 표시되지 않은 커맨드는 실행하지 않는다 | 실행 래퍼가 사전 공개된 argv로만 호출되는지 검사 (검증 도중 별도 승인은 받지 않음 — `ARCHITECTURE.md` 신뢰 경계) |

## MVP 제외 사항
- **~~자동 소스측 패턴 채굴 (개방형 발견) = E2 비전~~ → phase 3에서 본선 승격** — 사용자가 저장소만 지정하면 앱이 방법론을 스스로 발견해 후보로 제안하는 개방형 발견은 MVP·phase 2에서 제외였으나, **제품 루트로 승격됐다**(ADR-017). 실현 가능성은 성격이 다른 세 저장소를 대상으로 한 스파이크에서 확인했다 — 아래 'Phase 3 범위' 참조.
- **EXTRACT·ABSTRACT의 앱 구현 (MVP 한정 제외 — phase 2에서 해제)** — MVP에선 카탈로그 제작이 **오프라인 손 큐레이션 절차**였고 앱이 구현한 것은 INSTANTIATE·VERIFY뿐이었다. phase 2는 대상 지정 추출로 EXTRACT·ABSTRACT를 앱 안에 들인다(아래 'Phase 2 범위' 참조). 핵심 가치가 ABSTRACT라는 것(ADR-004)을 이제 앱이 실제로 수행한다.
- **N=1(`observed`) 패턴의 생성** — experimental 옵트인으로 지연. MVP는 `corroborated`만 생성.
- **비게이트형 방법론의 이식** — 서술 전용. 검증 불가한 것은 옮겨 심지 않는다.
- **유사 프로젝트 추천 / "내 repo에 어떤 방법론이 빠졌는지" 진단** — 별도 트랙이 아니라 **핵심 기능 2번의 제품 표면**이지만(위 '핵심 기능'), **선행 조건이 충족되기 전까지 착수하지 않는다**: 단일 저장소 분석 결과가 저장소 간 비교가 가능한 **공통 스키마**로 나온다는 것이 먼저 검증돼야 한다. "비슷함"을 판정할 축이 데이터 모델에 없는 상태에서 만들면 근거 없는 매칭이 된다.
- **자생 vs 상속 구분** — SURVEY 결과가 그 저장소가 만든 규율인지 템플릿에서 상속된 것인지 가르는 축은 실재하는 문제지만, **검증 가능한 판정 신호가 마련되기 전까지 생성 결과의 분류 축으로 쓰지 않는다**(ADR-019). 그때까지 이 한계는 결과 화면에서 숨기지 않고 밝힌다.
- **다중 패턴 워크플로우 조합** — MVP는 단일 패턴(Spec↔Verify) 하나만 깊게.
- **호스팅된 공유 레지스트리 / 기여 인프라 / 승급 자동화** — 커먼즈는 포터블 파일 포맷 + 로컬 카탈로그로만 실재.
- **다중 타깃 스택** — MVP 타깃은 JS/TS(vitest) 하나. (단, 소스 스택 ≠ 타깃 스택은 필수 — 아래 참조.)

## Phase 2 범위 — 카탈로그 저작 (EXTRACT·ABSTRACT)
MVP가 INSTANTIATE·VERIFY(이식·증명)를 앱으로 닫았다면, phase 2는 그 **앞단**을 앱으로 들인다 — 카탈로그를 손이 아니라 앱이 저작한다. 이번 phase의 목표는 **하드코딩 없는 범용 분석 파이프라인의 기반**을 세우는 것이다: 사용자가 소스 저장소 ≥2개와 의도를 주면, 앱이 provenance 기반으로 근거를 수집·대조해 패턴 초안을 제안하고, 사용자가 검토·승인한 뒤에만 카탈로그에 저장한다.

**범위의 정직한 경계.** "어떤 저장소에도"는 **분석 대상(소스) 측**을 뜻한다 — 이식 타깃은 ADR-013(JS/TS vitest) 그대로다. **분석(EXTRACT·ABSTRACT)과 `descriptive` 등재까지는 완전 범용**이고, **`generative`의 이식·검증은 현재 엔진이 합성하는 앵커 형태(3역할)에 한정**한다. 임의 패턴의 자동 합성·이식은 이번 범위 밖(후속 phase). 사용자가 저장소만 지정하면 앱이 방법론을 스스로 발견하는 개방형 발견은 phase 2 시점에 E2 비전이었으나 **phase 3에서 SURVEY로 승격됐다**(ADR-017 — 아래 'Phase 3 범위').

**입력.** 사용자는 소스 저장소(`UPTAKE_SOURCE_ROOT` 아래)와 **추출할 방법론의 의도(intent)**만 지정한다. 앱(LLM proposer)이 role·binding·provenance 후보로 초안을 제안하고, 사용자는 **승인/거부만** 한다(후보 편집은 후속). `revision`은 저작 개시 시점 HEAD SHA로 자동 고정한다.

요구사항(착수 시 수용 기준으로 물질화):
- **대조 근거 ≥2 독립 저장소.** `corroborated` 패턴은 최소 2개의 독립 저장소가 있어야 생성 가능하다. 독립성·역할 단위 대조 판정은 기존 층 1 하드 게이트 기준을 그대로 쓴다(AC-1·AC-2b).
- **모든 근거에 파일 경로 + revision provenance.** 근거는 저작 개시 시 고정한 커밋 SHA에 결속되며, resolve되지 않는 주장은 초안에 담기지 않는다(ADR-009). resolve는 기존 루트 기반 계약을 그대로 재사용한다.
- **저장소 내용은 불신 데이터.** EXTRACT가 읽는 소스 저장소 내용은 지시가 아니라 데이터로 격리한다. 읽기 전용이며 실행하지 않는다(신뢰 경계).
- **공통점=role 후보 / 차이점=binding 후보.** 소스 간 대조로 공통점은 `roles`(본질) 후보로, 차이점은 `bindingPoints`(파라미터) 후보로 분리한다. **`corroborated` 저작에 한해** 단일 저장소(단일 `independenceGroup`)만 지지하는 role 후보는 role이 아니라 binding으로 내려간다(ADR-005).
- **판정은 사용자 몫.** `independenceGroup`·`isTargetStack`·"공통점이 본질"의 **최종 해석·승인은 사용자**가 한다. 앱은 provenance·target stack 탐지 결과 등 **결정적 사실과 그 근거를 자동으로 제시**할 수 있으나, 판정을 대신 내리지 않는다(ADR-005).
- **LLM은 후보만(ADR-015).** EXTRACT·ABSTRACT·oracle 초안은 proposer 포트를 통한 LLM 후보이고, 수용 기준 테스트는 이 포트를 **스텁**으로 주입해 결정적 기계만 검증한다.
- **환각 봉쇄(AC-C9).** proposer가 resolve 불가 근거·단일 repo 지지 role·판별력 없는 oracle을 제안하면 각각 등재가 거부되고 사유가 보고된다.
- **승인 전 catalog 미기록.** 초안은 승인 전까지 카탈로그에 쓰지 않는다. 승인 시에만 `catalog/<patternId>.json`으로 기록한다(타깃 쓰기의 AC-10과 대칭).
- **씨앗 보호(AC-C10).** 등재는 기존 `catalog/` 파일을 덮어쓰지 않는다. patternId 충돌 시 등재가 거부되고 기존 파일은 불변이다(기존 패턴 편집·교체는 후속).
- **승인된 패턴은 기존 하드 게이트 통과.** 등재되는 패턴은 층 1 하드 게이트(provenance resolve·참조 무결성·독립성/스택·`capability`↔`oracle` 일치)를 기록 전·후로 통과해야 한다.
- **oracle 자기검증.** generative 초안의 oracle은 앱이 초안하되, 등재 전에 **번들 정규 fixture 타깃**에 대해 실제 VERIFY(양성 green + 음성 red)를 돌려 판별력을 입증한 것만 등재한다(ADR-016). 앵커 형태에 한정한다.
- **전체 흐름 연결(앵커 형태).** 앱이 저작·등재한 앵커 형태 generative 패턴 하나가 곧바로 INSTANTIATE(역할 형태 매칭)→VERIFY로 이식·검증까지 이어진다(E2E 1건).

세부 설계는 `ARCHITECTURE.md`의 'EXTRACT·ABSTRACT 저작 계약', 결정 근거는 `ADR.md`의 ADR-014~016을 따른다.

## Phase 3 범위 — 발견 (SURVEY)
phase 2까지의 제품은 **사용자가 무엇을 추출할지 안다**는 전제 위에 섰다. 그 전제를 폐기하고 발견을 제품 루트로 올린다(ADR-017).

**이번 phase의 목표는 하나다 — 저장소 하나를 넣어 그 저장소의 개발 체계를 실제로 읽을 수 있는, 가장 얇은 end-to-end.** 엔진·API·UI·E2E를 모두 관통하되 각 층은 최소로 만든다. 폭을 넓히는 것(추천·다중 저장소·자동 이식)은 이번 범위가 아니다.

**입력**: 저장소 하나(`UPTAKE_SOURCE_ROOT` 아래). intent는 받지 않는다 — 앱이 제안한다.
**출력**: 개발 체계 후보 목록. 사용자가 고른 후보가 `observed`/`descriptive` 패턴으로 카탈로그에 등재된다.

요구사항(착수 시 수용 기준으로 물질화):

- **intent를 입력받지 않는다.** 사용자는 저장소만 지정한다. 각 후보는 의도 서술과 근거 경로를 달고 나오며, 사용자는 승인/거부만 한다(ADR-017).
- **수집 규칙은 확장 가능한 데이터다.** "어디를 볼까"는 결정적 규칙이 정하고 "그것이 무슨 방법론인가"는 LLM이 판단한다. 규칙을 코드에 박지 않으며, **카테고리별 예산 배분**으로 한 카테고리가 전체를 독식하지 못하게 한다(ADR-018).
- **모든 후보 근거는 고정된 revision에서 resolve된다.** 저장소 HEAD SHA를 개시 시점에 고정하고, resolve되지 않는 근거를 단 후보는 폐기하며 **폐기 사유를 사용자에게 보인다**(ADR-009 · phase 2의 AC-C9와 동일 기준).
- **저장소 내용은 불신 데이터다.** 읽기 전용이며 실행하지 않고, 프롬프트 지시가 아니라 데이터로 격리한다(신뢰 경계).
- **LLM은 후보만 낸다.** SURVEY도 proposer 포트를 거치며, 수용 기준 테스트는 그 포트를 **스텁으로 주입**해 결정적 기계만 검증한다(ADR-015).
- **승인 전 catalog 미기록.** 사용자가 고르지 않은 후보는 카탈로그에 쓰지 않는다. 기존 `catalog/` 파일을 덮어쓰지 않는다(phase 2의 AC-C10과 동일).
- **등재물은 기존 하드 게이트를 통과한다.** `observed` 패턴은 독립 그룹이 정확히 1이어야 하고, 참조 무결성·`capability`↔`oracle` 일치를 기록 전·후로 만족해야 한다(층 1 게이트 재사용).
- **한계를 화면에서 밝힌다.** 자생/상속을 구분하지 않는다는 것(ADR-019), `observed`는 "이 repo가 실제로 이렇게 한다"까지만 주장한다는 것(ADR-006)을 결과 화면이 숨기지 않는다.
- **전체 흐름 연결.** 저장소 지정 → 후보 제시 → 선택 → 등재 → 카탈로그에서 읽기가 관통하는 E2E 1건. 결정적·오프라인(스텁 proposer)으로 돈다.

**이번 범위 밖** — 유사 프로젝트 추천(공통 스키마 검증이 선행), 자생/상속 분류 축(판정 신호가 선행), 다중 저장소 동시 분석, `observed`→`corroborated` 자동 승급, generative 패턴의 자동 합성(앵커 형태 한정은 ADR-014 그대로).

## Phase 4 범위 — 워크플로우 배포 ①: 파일 릴레이 (`init` → `survey` → `author`)
phase 3까지의 제품은 기능을 갖췄으나 **단계가 서로를 모르고, 진행 상태가 프로세스와 함께 사라진다.** SURVEY·저작·이식 세 위저드는 각자 인메모리 저장소에 살며, 앞 단계의 산출물을 뒤 단계가 읽는 경로가 없다. phase 4는 uptake의 방법론을 **다섯 단계의 명령으로 명시하고 산출물을 디스크로 내려** 릴레이를 성립시킨다(ADR-020). 이번 phase는 그 앞 세 단계까지다.

**목표는 하나다 — `uptake init` → `uptake survey` → **프로세스 종료** → `uptake author`가 디스크에서 이어받아 기존 엔진으로 초안을 만드는 것.** 새 기능을 만들지 않는다. 엔진·게이트는 그대로 재사용하고, 워크플로우 층(명령 표면 · 산출물 영속화 · 선행조건 검사)만 얹는다.

```
uptake init                    → .uptake/METHOD.md
uptake survey <repository>     → runs/NNN-<slug>/survey.json · runs/current
        ── 프로세스 종료 ──
uptake author --candidate <id> → runs/<current>/authoring.json  (성공 시 pattern 포함)
```

**`author`는 SURVEY 후보 채택 경로 하나만 태운다.** 두 번째 소스를 대조하는 저작(`--source`)과 `generative` 승격은 이번 범위가 아니다 — 채택과 대조 저작은 서로 다른 기계이고, SURVEY 후보를 `generative`로 승격하려면 사용자가 화면에서 보고 고른 근거를 버리고 LLM 재추출을 해야 한다(ADR-023). phase 4의 채택 산출물은 항상 `descriptive`/`observed`다.

**`author`는 카탈로그에 등재하지 않는다.** 5단계 체인 어디에도 등재된 카탈로그를 **되읽는 단계가 없다** — `verify`는 앞 단계의 산출물을 읽는다. 릴레이를 세우는 phase에 write-only 산출물을 넣지 않으며, 등재는 카탈로그를 실제로 소비하는 단계와 함께 설계한다. 따라서 층 1 하드 게이트는 phase 4에서 걸리지 않고 **소비 시점에 걸린다**(ADR-025).

요구사항(착수 시 수용 기준으로 물질화):

- **방법론이 파일로 배포된다.** `uptake init`이 `.uptake/METHOD.md`에 원칙과 단계 체인을 쓴다. 이 문서는 **설명이며 집행 주체가 아니다** — 편집해도 게이트는 바뀌지 않고, 게이트의 정본은 코드다. 각 원칙에는 집행 게이트의 **상태 이름**만 붙인다(`file:line` 참조 금지 — 드리프트를 만든다). `init`은 멱등이며 기존 파일을 덮어쓰지 않고, 네트워크에 나가지 않는다. **산출물은 `METHOD.md` 하나다** — 설정 파일은 실제로 결정할 것이 생길 때 도입한다.
- **미구현 단계를 정직하게 표현한다.** `METHOD.md`는 다섯 단계 체인을 원칙과 함께 적되 **현재 배포된 명령이 `init`·`survey`·`author`임을 밝힌다**. CLI는 아는 명령 셋 외에는 전부 unknown으로 처리해 사용 가능한 명령 목록을 출력하고 `exit 2`로 나간다 — `verify`·`apply`라는 이름을 코드가 갖지 않는다. `author` 성공 메시지는 다음 명령 대신 "여기까지가 현재 배포된 워크플로우"를 말한다.
- **콜드 스타트는 해소하지 않고 설명한다.** `init`은 네트워크에 나가지 않으므로 씨앗 저장소(`.uptake/sources/` 아래)를 받아오지 못한다. 근거 저장소가 없으면 그 패턴은 `provenance-unresolved`로 거부되며, 이는 정상 동작이다. `METHOD.md`가 어떤 소스를 왜 받아야 하는지 설명한다.
- **경로가 분리된다.** 패키지 동봉 자산은 **설치 위치** 기준으로, 사용자 상태(`.uptake/`)는 **프로젝트 루트** 기준으로 해석한다(ADR-024). 이번 범위의 대상은 **둘뿐이다** — `survey-rules.json`(모듈 import로 경로 해석 자체를 없앤다)과 `templates/`(`init` 전용이므로 설치 위치 해석). 명령이 uptake 저장소 밖에서 실행돼도 동작하며, 그 사실을 통합 테스트가 확인한다.
- **산출물이 릴레이된다.** 각 단계는 `.uptake/runs/<id>/` 아래에 산출물을 쓰고, 다음 단계는 인자 없이 `runs/current`가 가리키는 run에서 그것을 찾아 읽는다. 프로세스 경계를 넘어 이어진다. **`survey`는 항상 새 run을 만들고 `current`를 갱신한다** — 재개는 뒤 단계의 성질이지 `survey`의 성질이 아니다. 여러 run 중 다른 것을 고르려면 `current`를 고쳐 쓴다.
- **세 상태를 디스크에서 구분한다.** 미실행(파일 부재) / 실행·실패(파일 존재 + 실패 판별자) / 실행·성공(파일 존재 + 성공 판별자). **게이트 실패도 산출물을 남긴다** — 실패 코드·폐기 근거·고정 revision을 구조화해 기록하고, 다음 단계가 소비할 성공 산출물만 만들지 않는다. **한 단계의 상태는 한 파일에만 산다** — `status`를 싣는 파일은 단계당 하나이고(`survey.json`·`authoring.json`), 성공 판별자가 두 파일에 걸치지 않는다. 크지 않은 산출은 그 파일 안의 필드로 담는다(`authoring.json`의 `pattern`). **revision이 이미 고정된 뒤의 실패는 예외 없이 revision을 싣는다** — 지금 싣지 않는 실패 분기는 필드를 넓힌다(상태를 추가하는 것이 아니다).
- **선행조건이 워크플로우를 가르친다.** 앞 단계 성공 산출물이 없으면 실행하지 않고 다음에 칠 명령을 알려준다. 미실행·실패 두 경우 모두 검사한다.
- **고정 revision을 그대로 소비한다.** `author`는 `survey.json`에 기록된 revision을 쓰고 **HEAD를 다시 읽지 않는다.** 읽을 수 없을 때만 `revision-unresolvable`·`provenance-unresolvable`로 실패한다(ADR-021).
- **채택 경로의 게이트는 그대로 걸린다.** 근거의 provenance resolve(resolve 실패분은 사유와 함께 폐기) · 참조 무결성 양방향 · `observed`는 독립 그룹 정확히 1 — 채택 경로가 이미 거는 것들이 CLI에서도 그대로 걸리고, 거부는 실패 산출물을 남긴다. **카탈로그 층 1 하드 게이트 전체와 `generative` 전용 게이트(앵커 형태 · oracle 자기검증)는 이번 범위가 아니다** — 전자는 소비 시점으로(ADR-025), 후자는 승격과 함께(ADR-023) 옮긴다.
- **소비 가능한 형태로 직렬화한다.** `authoring.json`의 `pattern`은 `validatePatternValue`가 **그대로 먹는 형태**여야 한다. 소비 단계가 그 함수로 층 1 게이트를 다시 걸기 때문이다(ADR-025).
- **웹 회귀가 통과한다.** phase 4는 웹 **코드**를 건드리지 않지만 공유 엔진 변경이 웹 **동작**을 바꾼다(`revision-moved` 제거 · `no-signal` 필드 · 수집 규칙 로딩). 기존 회귀가 `npm run test:e2e`를 포함해 통과해야 한다. `revision-moved` 제거로 무효가 되는 테스트는 **교체**하되, E2E를 통과시키려고 고치지 않는다(`e2e/`는 회귀 방지 증거다).
- **전체 흐름 연결.** 별개 프로세스로 `init`·`survey`를 돌리고 종료한 뒤, 새 프로세스의 `author`가 관통하는 통합 테스트 1건. 결정적·오프라인(스텁 proposer)으로 돌고, **uptake 저장소 루트가 아닌 작업 디렉터리에서** 실행한다.

**이번 범위 밖** — **카탈로그 등재(카탈로그를 되읽는 단계와 함께 설계 · ADR-025)**, **`--source`를 통한 대조 저작과 `generative` 승격(ADR-023)**, `verify`·`apply`(phase 5), 설정 파일(`config.json`)·실행 원장(`run.json`), 씨앗 카탈로그·자기검증 fixture의 경로 분리(그 경로를 CLI가 실행하는 phase에서), 웹 UI 개편, 웹의 상태 영속화, 에이전트 커맨드 설치, CLI 배포·번들링(`npm link`까지), presets·extensions·bundler 대응물, 이식 산출물의 파라미터화.

## Phase 5 범위 — 워크플로우 배포 ②: 검증·적용 (`verify` → `apply`)
phase 4가 세운 릴레이를 이식까지 잇는다. 승인 경계를 저장 방식에서 떼어내는 것이 이번 phase의 핵심 리스크다(ADR-022).

요구사항(착수 시 수용 기준으로 물질화):

- **소비 직전에 층 1 하드 게이트를 건다.** `verify`는 `authoring.json`의 `pattern`을 읽은 직후 `validatePatternValue`(웹의 `loadCatalog`가 부르는 그 함수)를 걸고, 통과하지 못하면 실패 산출물을 남기고 중단한다. CLI는 카탈로그를 거치지 않으므로 층 1 보증이 여기서 만들어진다 — 이것이 없으면 산출물을 손으로 고쳐 provenance를 지어내도 VERIFY가 잡지 못한다(ADR-025).
- **검증된 생성물이 산출물로 고정된다.** `verify`가 instantiate한 **정확한 파일들**을 기록하고, `apply`는 다시 생성하지 않고 그 파일을 읽어 적용한다.
- **해시 3중 대조.** `contentHash`(생성물) · `bindingsHash`(해소된 바인딩) · `targetBaseHash`(타깃 트리)를 검증 시점에 고정하고 적용 직전 재계산해 대조한다. `bindingsHash`는 `contentHash`로 대체되지 않는다 — 현재 엔진은 바인딩 중 checker만 생성에 쓰므로, 바인딩을 바꿔도 생성물이 변하지 않는다.
- **승인은 대화형 한 프로세스 안에서.** `apply`가 검증 결과와 적용 파일을 보이고 승인을 받아 즉시 적용·소비한다. 자동 승인 플래그와 산출물 직접 편집은 공식 경로가 아니며, stdin이 TTY가 아니면 실패한다.
- **엔진은 승인 입력만 받는다.** 저장 방식 어휘를 엔진에서 제거하고, 소비 봉인은 표면별 책임으로 둔다. 웹 경로의 기존 동작과 테스트는 유지된다.
- **양성 green AND 음성 red만 통과.** 음성이 green이면 `negative-not-caught`, 리포터를 못 만든 실행은 `gate-error`·`timeout`이며 red로 세지 않는다(ADR-008 그대로).
- **재적용 차단.** 소비된 검증 산출물로 다시 적용할 수 없고, 타깃이 승인 후 바뀌면 `base-changed`로 거부한다. 두 방어를 각각 검사한다.
- **전체 흐름 연결.** `init` → `survey` → `author` → `verify` → `apply` 5단계 관통 통합 테스트 1건.

**이번 범위 밖** — **카탈로그 등재**(phase 5도 카탈로그를 되읽지 않는다 — `verify`는 `authoring.json`을 읽는다. 등재는 카탈로그를 실제로 소비하는 단계가 생길 때 그 단계와 함께 설계한다 · ADR-025), 이식 산출물의 진짜 파라미터화(생성 경로·oracle·미사용 바인딩은 앵커 고정 그대로), 웹 UI 개편, CLI 배포.

## 데모의 필수조건 (대회 legibility)
MVP는 **소스 스택 ≠ 타깃 스택**으로 이식을 시연한다(예: PHP repo에서 관찰 → JS/TS repo에 이식). 소스와 타깃이 같은 스택이면 "복사"와 구별되지 않아 핵심 가치(B)를 증명하지 못한다. 데모는 하나의 `corroborated` 패턴을 **끝까지 깊게**(고름 → 결합점 탐지 → 이식 → 양성/음성 검증 → diff 승인) 보여준다.
